# 単一primaryの書き込みの限界を観察する

掲示板の投稿処理（`post.Service` → `board.posts` へのINSERT）を並列に呼び、primary 1台がどこで頭打ちになり、
そのとき何を待っているかを記録する。ここで得た値は、後の対策（単一ノードでの工夫、パーティション分割）を比べる基準になる。

答える問い:

1. 並列数を上げたとき、スループットはどこで頭打ちになり、その後レイテンシはどう伸びるか
2. 頭打ちの原因はどこか（WALのfsync / CPU / 行ロック / 接続数 / 計測側）
3. 1スレッドへの集中書き込みは、分散書き込みより少ない並列数で詰まるか
4. 書き込み負荷でレプリカの遅れはどう伸びるか

## 実行

```sh
make db-up
make load-observe                          # 負荷なしで観測だけを10秒。観測が動くことの確認
make load-closed                           # 1a: 1000スレッドへ分散、並列数 1,2,4,…,64
make load-closed THREADS=1                 # 1b: 全ワーカーが同じスレッドへ書く
make load-open RATES=4000,7000,8500 POOL=16  # 一定レートで送る。飽和点はclosedの結果から決める
make load-closed LOAD_ARGS='-warmup 2s -duration 10s'  # 短く試す
```

各段は慣らし5秒＋計測30秒。段の間ではレプリカが追いつくまで待つ（最大60秒）。
結果は `results/<日時>/` に出る（git管理外）。最後に段ごとの表を表示する。

負荷生成器は既定で Compose ネットワーク内のコンテナ（`loadgen` サービス、CPU 4）から接続する。
ホストから `127.0.0.1:15432` 経由で接続すると Docker Desktop のポート転送が律速になり、
PostgreSQL ではなくそれを測ってしまう（並列数16で約2,100/s、ネットワーク内からは約8,000/s）。
比較のために `LOADGEN_AT=host make load-closed` でホストからも実行できる。

## 実験の構成

| ID | 負荷 | 何を見るか |
|---|---|---|
| 1a | 1000スレッドへ一様に分散（`THREADS=1000`） | 並列数を上げたときの飽和点と、そのときの待ち |
| 1b-0 | 全ワーカーが1スレッドへ書く。レス番号なし（002適用前のアプリ） | 同じスレッドへ書くこと自体はホットスポットになるか |
| 1b-1 | 全ワーカーが1スレッドへ書く。レス番号あり（`THREADS=1`） | スレッドの行の採番がコミットまで直列化するとどうなるか |
| open | 1aの条件で一定レートを送る | 容量の手前・直後でレイテンシと待ち行列がどう変わるか |

レス番号（`infra/postgres/migrations/002_post_number.sql`）を入れてからは、投稿1回が
`BEGIN → UPDATE threads（採番）→ INSERT posts → COMMIT → LSN取得` になる。
UPDATE で取ったスレッドの行のロックは COMMIT のfsyncが終わるまで保持されるので、
1スレッドあたりの上限は並列数によらず `1 / ロック保持時間` 付近になるはず。
1b-0 は 002 より前のアプリでしか再現できない。

## 負荷のかけ方

`cmd/loadgen` は HTTP を通さず、`cmd/server` と同じ `post.Service` と Repository をプロセス内で呼ぶ。
投稿1回は「INSERT」と「書き込み位置（LSN）の取得」の2往復になる。これも実アプリのコストとして含める。
実行ごとに新しいユーザーとスレッドを作り、既存データには書き込まない。

- **closed**: N個のワーカーが、前の投稿の完了を待ってから次を送る。並列数ごとの飽和点を探す。
  サーバーが詰まると送信も止まるので、待ち行列の伸びは見えない。
- **open**: 完了を待たずに一定間隔で送る。レイテンシは予定時刻から測り、接続待ちも含める。
  容量を超えると待ち行列が際限なく伸びる。`in_flight` がその長さ。

接続プールの最大数は `-pool`（closedでは既定で最大並列数）。pgxpool の既定は max(4, CPU数) なので、
指定しないと並列数を上げてもクライアント側で待つだけになる。`poolwait` はそのクライアント側の待ち。

## 読み方

**Littleの法則**: `L = スループット × 平均レイテンシ`。closed では並列数とほぼ一致する。
飽和した後はスループットが横ばいになり、平均レイテンシだけが並列数に比例して伸びる。

**待ちの内訳**（`sessions`）は、負荷用の接続（`application_name = ddia-loadgen`）を0.1秒ごとに数えた平均の本数。

| 表示 | 意味 |
|---|---|
| `LWLock:WALWrite` | 他のプロセスがWALを書き出し・fsyncし終わるのを待っている |
| `IO:WalSync` | 自分がWALをfsyncしている。WALの書き出しは一度に1プロセスなので、ほぼ1を超えない |
| `IO:WalWrite` | WALをOSへ書いている |
| `Lock:transactionid` / `Lock:tuple` | 他のトランザクションが更新中の行のロック待ち |
| `CPU` | 待ちのない active。実行中（計装されていない待ちも含む） |
| `Idle` | サーバーはクライアントからの次の要求を待っている。プール内で未使用、往復の途中、2つのクエリの間 |
| `IdleInTransaction` | トランザクションの途中でクライアントを待っている。行ロックを持ったままのことがある |
| `Client:ClientRead` | クエリの途中でクライアントからのデータを待っている |

**`ins/fsync`** は、WALのfsync 1回でまとめてディスクへ書けた投稿の数（グループコミット）。
LSNを読むSELECTもコミットに数えられるがfsyncしないので、コミット数ではなく投稿数で割っている。
fsyncの回数は1秒あたりおよそ `1 / fsync時間` で頭打ちになり、それ以上はまとめる数を増やすしかない。

統計ビュー（`pg_stat_database`、`pg_stat_io` など）はバックエンドが約1秒ごとにまとめて反映するので、
1秒ごとの値は揺れ、約1秒遅れる。比較には計測窓全体の値を使う。WALの量だけはLSNの差で即時に測っている。

## 環境の注意

この値は手元のDocker Desktopでの相対比較にだけ使う。

- **CPU上限**: PostgreSQL の各ノードは `cpus: 2`、`mem_limit: 1g`（`infra/postgres/compose.yaml`）。
  上限がないとVMのCPUを奪い合い、後でノードを足しても容量が増えたことにならない。
- **fsyncの絶対値**: VMの仮想ディスクを経由するので、本番の参考にならない。
- **VMの停止**: Docker Desktop のVMは、負荷がなくても約10秒ごとに数百ms止まることがある（書き込み負荷中は約700ms）。
  同じVMで他のプロジェクトのコンテナが動いていると起きやすい可能性がある。
  負荷生成器は20msごとのタイマーで自分の停止を記録し、`stall` に出す。
  `stall` を伴うレイテンシの山は環境のもの。`stall` を伴わない山はDB側（例: fsyncが1回遅れて全員が待った）。
- **WALの保持**: レプリカが遅れると、primaryはスロットのためにWALを残す。上限 `max_slot_wal_keep_size=2GB` を超えると
  スロットが失効し、レプリカの作り直しが必要になる。負荷生成器は残りが512MBを下回るか `wal_status` が
  `unreserved` / `lost` になったら中断する（`-slot-guard-mb`）。書き込みが多いと、遅れたレプリカは
  「primaryのディスクを埋める」か「切り捨てられる」かのどちらかになる。
- `make db-test`（WAL適用の停止を伴う）と同時に実行しない。
- `board.posts` は実行のたびに大きくなる。実行前の推定行数とサイズを `meta.json` に残す。

## 観察（2026-10-11、Apple Silicon の Docker Desktop、primary は CPU 2）

各条件1回ずつの実行。同じ条件でも fsync の速さが実行ごとに揺れ、並列数1で 690〜1,370/s の差が出た。
数値は傾向として読む。

**1a: 分散書き込み**（レス番号あり。投稿1回 = BEGIN・UPDATE・INSERT・COMMIT・LSN取得）

| 並列数 | 1 | 4 | 16 | 32 | 64 |
|---|---|---|---|---|---|
| 投稿/s | 690 | 2,113 | 3,998 | **4,507** | 3,683 |
| 平均ms | 1.5 | 1.9 | 4.0 | 7.1 | 17.4 |
| fsync 1回あたりの投稿 | 1.0 | 1.4 | 4.8 | 7.8 | 12.1 |
| primary CPU（コア） | 0.6 | 1.1 | 1.7 | 1.9 | 1.9 |

- fsync は1秒に約1,400回が上限（1回約0.7ms）。そこから先はグループコミットで1回のfsyncに多くのコミットを載せて伸びる。
  待ちの首位は `LWLock:WALWrite`（他のプロセスのfsync待ち）で、`IO:WalSync` はほぼ1本。WALの書き出しが1点に集まっている。
- 並列数32でCPUが上限（2コア）に届き、64ではスループットが下がる。CPU上限で止められた時間（`thr_ms`）も急増する。
  WALを書き出す1プロセスが止められると全員が待つ。
- レス番号の前（`results/20261011-091653`）も並列数32で 5,746/s が最大で、64で下がった。

**1b: 1スレッドへ集中**

| 並列数 | 1 | 4 | 16 | 64 |
|---|---|---|---|---|
| 1b-0 レス番号なし 投稿/s | 956 | 1,735 | 5,014 | 5,530 |
| 1b-1 レス番号あり 投稿/s | 896 | **1,199** | 960 | 706 |
| 1b-1 平均ms / p99 ms | 1.1 / 3.8 | 3.3 / 9.2 | 16.7 / 86 | 90.6 / 606 |

- 1b-0 では `Lock:*` の待ちが出ない。同じスレッドへのINSERT同士は衝突せず、外部キー確認の KEY SHARE ロックも両立する。
  同じスレッドへ書くこと自体はホットスポットではない（インデックスの同じページの奪い合い `LWLock:BufferContent` は増える）。
- 1b-1 は並列数4で頭打ちになり、その後は並列数を上げるほど下がる。待ちは `Lock:transactionid`（前の投稿のコミット待ち）と
  `LWLock:LockManager`（ロック管理そのものの奪い合い、並列数64で24本）。CPUは上限に届いていない。
- fsync 1回あたりの投稿は常に1.0。1つの行を通る投稿は1件ずつしかコミットできないので、グループコミットが効かない。
  1スレッドあたりの上限はスレッド単位でパーティションを分けても変わらない。

**open: 1aの条件で一定レート**（プール32、1aの最大 4,507/s に対して）

| 送信レート | 達成 | p50 | p99 | 待ち行列の最大 |
|---|---|---|---|---|
| 2,250/s（50%） | 2,264/s | 3ms | 1.4s | 約1,800 |
| 4,050/s（90%） | 4,050/s | 255ms | 2.1s | 約8,200 |
| 4,950/s（110%） | 4,557/s | 3.7s | 5.8s | 2万以上で増え続ける |

- 50%でも約10秒ごとの停止で1,500件ほど溜まるが、余力が2倍あるので2秒で解消する。
- 90%では primary のCPUがすでに上限で、1回の停止（DB側のfsyncが10ms超に伸びた）で溜まった8,000件の解消に約5秒かかる。
  計測時間の半分近くが回復中だった。
- 110%では待ち行列が減らず、レイテンシは時間とともに伸び続ける。closedではこれが見えない。

**複製の遅れ**: どの実行でも最大0.3MB・1秒未満。この書き込み量では、コミットごとにfsyncする primary が先に詰まり、
まとめて適用するレプリカは遅れなかった。
